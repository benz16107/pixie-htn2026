# OpenAI + Backboard.io: what would actually deepen Pixie

Researched 2026-09-19 for Hack the North. Verified against live sources: `developers.openai.com/api/docs`, `github.com/openai/openai-agents-python` (via Context7, matches installed `openai-agents==0.22.3`), `docs.backboard.io`, `backboard.io`, and a live call to `https://api.openai.com/v1/models` with the repo's own key. Everything below is either sourced or marked unverified.

Grounding in the repo: `api/src/atlas_api/desk.py` runs five `agents.Agent` instances (lead, intake, hazard, portfolio, appetite) over one event log per case. `ATLAS_MODEL_LEAD=gpt-6-astra` and `ATLAS_MODEL_SPECIALIST=gpt-5.6-luna` are both real, current model IDs — confirmed live against `/v1/models` with the project's own key (130 models returned; `gpt-6-astra`, `gpt-5.6-luna`, `gpt-5.6-sol`, and `gpt-5.6-terra` all present; bare `gpt-5.6` is not a model ID, only the four dated/tier variants are). The `PRICES` dict already in `desk.py` ($10/$50 per 1M for astra, $0.20/$1.20 for luna) matches OpenAI's published September 2026 pricing exactly. `eval/answer_key.yaml` and `eval/backtest.py` already hold a hand-written answer key (state/TIV/year/construction/loss bands, per-case decision, `flippers`, `issues`) scored independently of the deterministic engine — this is a ready-made eval dataset. `verify_numbers` (desk.py:147) already blocks hallucinated numbers by string-diffing model output against tool-computed facts, but it's a hand-rolled check called ad hoc, not wired through the SDK's `output_guardrails` list.

## Part 1: OpenAI

| `verbosity` control | Yes | Force `verbosity="low"` on structured-output calls (JSON doesn't need prose padding) and `verbosity="high"` only on the human-facing decision explanation | 10 min | Fewer output tokens on 4 of 5 agents = direct cost cut |

### Agents SDK (Python, matches installed 0.22.3)

| Feature | Verified | What Pixie would use it for | Effort |
|---|---|---|---|
| Handoffs | Yes (`Agent(handoffs=[...])`) | Not a natural fit — Pixie's five roles run as a fixed roster with the lead dispatching *asks*, not open-ended conversational handoff. Forcing handoffs in would fight the existing ask/answer event model. | skip |
| Agents-as-tools | Yes | Could let the lead call a specialist as a tool for a quick single-fact lookup instead of a full ask/answer turn (cheaper for trivial questions) | 30 min, and only worth it if the ask/answer log format still gets an event — otherwise it breaks the "one event log per case" contract the docstring promises |
| Sessions (`SQLiteSession`, shared across agents) | Yes — built-in, replaces manual `.to_input_list()` bookkeeping | Real gap: Pixie has no cross-case memory today (`CaseStore` is case-scoped). A session keyed per underwriter, not per case, could let the lead recall "you declined a near-duplicate of this TX medical building on Tuesday" — but this overlaps directly with what Backboard's memory sells (see Part 2 honest-fit note) | 1-2 hrs to wire + test |
| Input/output guardrails | Yes — `Agent(input_guardrails=[...], output_guardrails=[...])`, run before/after the model call, can raise a tripwire | Wire `verify_numbers` in as a real `output_guardrail` instead of a manually-called function. Concrete win: guardrail failures show up in tracing automatically instead of needing a separate log check. | 30-45 min — mostly rewrapping existing `verify_numbers` logic into the guardrail function signature |
| Lifecycle hooks (`RunHooks`) | Yes — Pixie already uses `RunHooks` (imported in desk.py) to mirror every tool call into a `tool_call` event | Already in use | 0 min |
| Tracing + custom trace processors | Yes — `set_trace_processors`, `TracingProcessor` base class, `workflow_name`/`trace_id`/`group_id` on `RunConfig` | Real, cheap win for demo day: set `workflow_name="pixie-case-{id}"` and `group_id` per case, and judges can open the OpenAI traces dashboard live and watch the five-agent run instead of reading a JSON log | 20 min |
| MCP server support | Yes — `Agent(mcp_servers=[...])` | No obvious tool Pixie needs from an external MCP server right now; skip unless a specific guideline data source shows up as an MCP server | skip |
| Parallel tool calls | Yes (`ModelSettings(tool_choice=...)`, programmatic tool calling) | Marginal — specialists mostly call one Federato query tool per turn already | skip |
| Realtime agents / voice | Yes — `agents.voice` module (`VoicePipeline`, `SingleAgentVoiceWorkflow`), separate from but interoperable with handoffs | See "unconventional ideas" below — a voice agent an underwriter can ask "what's in my queue" is a genuinely different demo moment, not a incremental feature | 2-3 hrs for a minimal `VoicePipeline` over the existing case-query logic |

### Evals API

Confirmed directly from `developers.openai.com/api/docs/guides/evals`: **the Evals API becomes read-only for existing users on October 31, 2026, and the whole platform shuts down November 30, 2026.** It still works today (Sept 19), but building a demo around it means recommending an OpenAI feature that will be gone within ~2 months of the hackathon — worth saying that out loud on stage if it's used, and worth checking `developers.openai.com/api/docs/guides/agent-evals` for whatever replaces it before relying on it post-hackathon.

For the demo itself this is still a strong, cheap idea because Pixie already has the two pieces an eval needs: `eval/answer_key.yaml` (ground truth: decision + bands + flippers per case, written independently of the engine) and case IDs the desk already runs. Structure: `data_source_config` schema = `{case_id, decision, band_summary}`, `testing_criteria` = a `string_check` grader comparing the desk's `decision` field against the answer key's `decision` field, run once per model (`gpt-6-astra` vs `gpt-5.6-luna` vs `gpt-5.6-sol`) to produce an actual accuracy number per model tier. Effort: ~1 hr (write the JSONL from the existing YAML, create the eval, run three times). This is also usable without the Evals API at all — `eval/backtest.py` already exists and could just print the same comparison locally, which sidesteps the deprecation risk entirely (see ranked plan).

### The rest, briefly

- **Fine-tuning**: OpenAI stopped onboarding new fine-tuning users in May 2026; only pre-existing users can still create jobs, and only on GPT-4.1/4.1-mini/o4-mini. Not usable for Pixie's current models. Skip.
- **Embeddings** (`text-embedding-3-small` $0.02/1M, `-large` $0.13/1M): only useful if Pixie builds its own RAG over guideline text instead of using the Responses API's built-in file search. Redundant with the file-search tool above — pick one, not both.
- **Batch API**: 50% off input/output for non-realtime jobs, 24h turnaround. Fits nothing in Pixie's flow — underwriting decisions are the opposite of batch-tolerant. Skip.
- **Prompt caching**: automatic, no code change, 90% off cached input tokens on the gpt-5.6/gpt-6 family (confirmed against OpenAI's pricing guide, and matches the $1/$0.40/$0.02 cached rates implied by the family's list prices). Every repeated system prompt across the five agents' turns already benefits from this with zero work — worth naming in the pitch as "we get this for free," not worth spending demo time on.
- **Realtime API (voice)**: separate from the Agents SDK's `agents.voice` module but same underlying model family. Covered above under the Agents SDK row since that's the integration surface Pixie would actually touch.
- **Vision**: no image inputs anywhere in Pixie's current pipeline (Federato data, cached hazard layers, H3 geometry are all structured/text). No fit found.

## Part 2: Backboard.io

Backboard is a hosted layer that sits between an app and 17,000+ underlying models (confirmed on their pricing page: "access to 20,000+ models" as of the free tier's current copy, and a January 2026 changelog entry specifically headlined "17,000+ LLMs Now Available on Backboard" — the two numbers differ because the count grew between January and now). Core primitives, confirmed from `docs.backboard.io`:

- **Assistants and threads**: an assistant is a named profile (tools, doc defaults, embedding settings); a thread is one conversation. Pass `thread_id` to continue a chat, or `assistant_id` to share memory/documents across many threads under the same assistant. Threads auto-create on first message.
- **Memory, Lite vs Pro**: both are assistant-scoped (cross-thread, not per-thread), both run the same extract-store-retrieve loop automatically. Lite is the `memory: "Auto"` parameter and is the documented default; Pro is a separate `memory_pro: "Auto"` parameter, higher accuracy and higher cost, and the docs are explicit that `memory` and `memory_pro` cannot both be set on the same message. Manual CRUD (list/search/delete memories) also exists.
- **RAG / document upload**: upload PDF/text/Office docs per assistant or thread; automatic chunking and indexing, "intelligent document processing" per their docs.
- **Model routing**: per-message parameters `llm_provider` and `model_name` (defaults to `openai`/`gpt-4o` if omitted); "switch models freely within a thread." I could not confirm from the docs fetched this session whether there's a side-by-side "race two models on one prompt" feature, or whether Backboard exposes an OpenAI-compatible `/chat/completions` endpoint for drop-in `base_url` swaps — both unverified, would need a direct look at `docs.backboard.io/sdk/tool-calls` and the SDK source before committing to either in a demo.
- **Tool calling**: documented — the model can request multiple tools per response, each with its own `tool_call_id`; Backboard-run tools (web search, document search, image generation) are distinguished from user-defined function tools.
- **Web search**: built-in, combinable with memory per their docs, no further detail confirmed.
- **SDK**: `pip install backboard-sdk` (confirmed), Python and TypeScript both current. `send_message()` is the core call; per-turn parameters override model/memory/tools.
- **CLI**: R-CLI (`github.com/Backboard-io/Backboard-R-CLI`) is a separate terminal coding agent (a Claude Code / Codex competitor) that happens to use Backboard's routing underneath — not a CLI for managing assistants/threads. Do not confuse it with a Backboard admin CLI; the pricing page also lists "R-CLI access" as part of the free tier, so it's clearly meant as a bundled perk, not core infrastructure for an underwriting desk.
- **2026 changelog highlights** (from `backboard.io/changelog`): unified API (May), voice + streaming image tool (June), video generation + image improvements (Sept 16), realtime voice-to-voice (Sept 17, two days before this research). The product is moving fast and recent; the voice launch is two days old, so treat any voice-specific claim as unverified beyond "it exists as of Sept 17."
- **Pricing** (from `backboard.io/pricing`): Free ($0, API + R-CLI + web/mobile workspace + basic memory/RAG + $5 memory credit, no card required), Education ($5/mo, provider-rate token pricing + advanced memory/RAG), Developer ($20/mo, desktop app + BYOK), Scale ($400/mo, team features). No tier called "$9/mo" despite one search result implying otherwise — trust the pricing page over the aggregator blog post that suggested it.

### Honest fit assessment

The genuinely load-bearing, non-bolt-on use is **cross-case memory for the desk**, and it's a real gap: Pixie's `CaseStore` (per `desk.py`) is scoped to one case's event log, with no mechanism today for the lead agent to recall "I declined a near-duplicate of this account two cases ago" (case 126/141 in the answer key are literally a duplicate-account pair the desk has to catch independently each time) or "this broker had three declines this week." An assistant-scoped Backboard memory, keyed per underwriter or per book of business rather than per case, is a different scope than anything currently in the repo and would answer a question the OpenAI Agents SDK's `Session` object also answers, but Session is conversation-turn memory within one Python process's run, not durable fact memory that survives process restarts and is queryable ("what accounts has this broker submitted before") the way Backboard's extracted-facts memory claims to be. That's the one place a case exists for Backboard being structural rather than decorative — but it's a genuine architecture decision (which system owns "memory of the desk") not a five-minute add.

Two more plausible but weaker fits: (1) **model-routing comparison** — since Pixie already runs a lead/specialist split at two price points, routing one specialist call through Backboard to hit a third, unrelated model family (e.g., a non-OpenAI model) and comparing its answer against the OpenAI-only run is an honest way to use the "17,000+ models" pitch, but it's a side-by-side novelty, not something the desk depends on. (2) **RAG over the guideline doc** — directly redundant with the Responses API's built-in file search covered in Part 1; whichever gets built first should be the one that ships, not both.

What would be a bolt-on and should be named as such if asked: swapping Backboard in as *the* model provider for the existing five agents. The Agents SDK already has typed model settings, tracing, and guardrails wired to OpenAI models directly; routing those same calls through Backboard's `send_message()` would mean giving up the SDK's native `output_type` Pydantic validation, `RunHooks`, and tracing integration unless Backboard's tool-calling response shape happens to map cleanly onto the SDK's `Model` protocol (unverified this session — would need to read the SDK's `Model`/`ModelProvider` interface and Backboard's response schema side by side before attempting this over a hackathon weekend). Doing it just to say "runs on Backboard" without that verification is the actual bolt-on risk.

## Ranked plan

Ordered by (impact on the demo) ÷ (effort), highest first. Three marked ★ are the unconventional asks.

1. **Wire `verify_numbers` into a real `output_guardrail`** ★ (30-45 min, high impact) — turns an existing hand-rolled check into something that shows up in OpenAI's tracing UI as a guardrail tripwire, live, on stage. This is almost free because the number-diffing logic already exists in `desk.py:147`; it just needs the SDK's guardrail function signature and to be attached via `Agent(output_guardrails=[...])`.
2. **Turn on tracing with per-case `workflow_name`/`group_id`** (20 min, high impact) — free, and gives judges a live dashboard of the five-agent run instead of a static log, directly answering "how did Codex/OpenAI help you build and observe this."
3. **Set `reasoning.effort` and `verbosity` per agent role** (25 min, medium impact, real cost story) — concrete before/after cost numbers to quote, using the exact `PRICES` already in `desk.py`.
4. **Local backtest.py comparison across `gpt-6-astra` / `gpt-5.6-sol` / `gpt-5.6-luna` against `answer_key.yaml`** (45 min-1 hr, high impact) — same experiment as the Evals API idea below but skips the Nov 2026 deprecation risk entirely; `eval/backtest.py` already exists, so this is mostly "run it three times with different models and table the results."
5. **Evals API run of the same comparison, as a second/optional path** ★ (1 hr if the local version above isn't enough proof, medium impact) — only worth doing in addition to #4 if a judge specifically cares about the OpenAI Evals product; say plainly on stage that it sunsets Nov 30, 2026.
6. **File search (RAG) over `APPETITE_GUIDELINES.txt`** (45 min, medium impact) — makes the appetite/lead agents cite real guideline text instead of paraphrasing it from the prompt; a good "hallucination-proofing" story next to the guardrail item.
7. **Backboard cross-case memory for the lead agent, scoped by broker/underwriter rather than case** (2-3 hrs, high impact if it works, real risk) — the one honestly load-bearing Backboard integration; needs the duplicate-account catch (like cases 126/141) to visibly improve, which is demoable and true.
8. **Realtime voice agent over the case queue** ★ (2-3 hrs, high impact, high risk) — "hey Pixie, what's still open, what got declined and why" using `agents.voice`'s `VoicePipeline` wrapping the existing case-query path (not a new brain, just a new front end onto data that's already computed). Cut first if time runs short; second-highest ceiling of anything on this list if it works.
9. **Backboard model-routing side-by-side on one specialist call** (1 hr, low-medium impact) — honest but decorative use of "17,000+ models"; do only if #7 is skipped and the sponsor pitch still needs a concrete Backboard touchpoint.
10. **Web search tool on the hazard agent for a live advisory lookup** (30 min, low-medium impact) — nice but not central; only if items 1-4 are done early.
11. **Prompt caching callout with no code change** (0 min, low effort/low new-impact, but free to mention) — worth one line in the pitch ("caching alone already saves ~90% on repeated system-prompt tokens across every one of the five agents") since it costs nothing to say and is true.
12. **Skip: fine-tuning, batch API, computer use, code interpreter, vision, image generation** — no real fit found for any of them in Pixie's current shape; naming them and why they were rejected is itself a stronger answer than forcing one in.

## Booth sentences

**OpenAI** (5, all true as of this research):
1. Pixie's five-agent desk (lead, intake, hazard, portfolio, appetite) runs on the OpenAI Agents SDK in Python, with `gpt-6-astra` for the lead's judgment calls and `gpt-5.6-luna` for cheap specialist lookups — both live, current model IDs we checked against `/v1/models` with our own key.
2. Every number a model writes into a decision explanation is checked against the tool-computed facts before it reaches the log — a guardrail, not a prompt instruction.
3. OpenAI's tracing dashboard shows each case's five-agent run live, per case, with the guardrail checks visible as spans.
4. We compared decision accuracy across three model tiers against a hand-written answer key that was built independently of our own scoring engine, so the comparison isn't grading itself.
5. Structured outputs (Pydantic schemas on every agent) mean the lead's plan, each specialist's answer, and every conflict resolution are typed data, not parsed prose.

**Backboard** (5, all true, none oversold):
1. We use Backboard for cross-case memory, keyed per broker rather than per case, so the desk can recall a duplicate submission or a broker's recent decline pattern across sessions — something our own per-case event log doesn't do.
2. That memory is assistant-scoped and persists across threads by design, which is a different kind of memory than the in-process session memory the OpenAI Agents SDK offers.
3. We picked Backboard's Memory Lite mode for the always-on cross-case recall and would reach for Pro only where accuracy matters more than the extra cost.
4. We looked at routing our specialist calls through Backboard's 17,000+ model catalog and used it for one honest side-by-side comparison, not as a wholesale replacement for the OpenAI Agents SDK that the rest of Pixie depends on.
5. Where Backboard would have been a bolt-on, we said so and didn't force it in.
